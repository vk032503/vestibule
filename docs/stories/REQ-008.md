# REQ-008 — Indexer

**Phase:** 2 · **Pipeline:** compressed (story → developer → reviewer, no LLD gate) · **GitHub issue:** #<open one>

## Goal
Write embedded chunks into a vector store, idempotently, so the same document ingested twice
overwrites rather than duplicates. This is the last component of Phase 2 — after this, a real
PDF flows end-to-end from blob to searchable vectors.

Two adapters ship: Azure AI Search for production, and an in-memory store so the full pipeline
runs with zero cloud credentials.

## In scope

### The Indexer orchestrator
- `Indexer.index(envelope, embedded_chunks) -> IndexResult`
- Owns the ledger transition: `indexing → indexed` on success; `indexing → indexing`
  (self-transition, TRANSIENT) on retryable failure; `indexing → failed` on PERMANENT failure
- All ledger writes route through `is_benign_concurrent_loss` triage
- Batches upserts per adapter's declared `max_batch_size`
- **Delete-before-upsert on version change**: if the store already holds chunks for this
  `doc_id` with a different `doc_version`, delete them all first, then upsert the new ones.
  This is what prevents orphan chunks when a document shrinks between versions.

### The IndexResult model
- `IndexResult`: `doc_id`, `chunks_upserted: int`, `chunks_deleted: int`,
  `index_name: str`, `embedding_model: str`, `embedding_dimensions: int`
- Frozen pydantic model — the receipt for what actually landed

### The IndexerAdapter interface
- Abstract base with:
  - `upsert(records: list[IndexRecord]) -> UpsertOutcome` — per-item success/failure, not all-or-nothing
  - `delete_by_doc_id(doc_id: str) -> int` — returns count deleted
  - `count_by_doc_id(doc_id: str) -> int`
  - `get_doc_version(doc_id: str) -> str | None` — for version-change detection
  - `ensure_schema(dimensions: int, metric: str) -> None` — idempotent; creates the index if absent
  - Properties: `index_name: str`, `max_batch_size: int`, `supports_hybrid: bool`
- `UpsertOutcome`: `succeeded: list[str]` (chunk_ids), `failed: list[tuple[str, str]]` (chunk_id, reason)

### The IndexRecord model
- Flat, store-agnostic representation of what gets written:
  - `chunk_id` (the key), `doc_id`, `doc_version`, `vector: list[float]`, `text: str`
  - `position: int`, `section_path: str | None`, `element_types: list[str]`, `strategy: str`
  - `allowed_groups: list[str]`, `trust_tier: str` — **security trimming metadata, carried
    from the envelope**
  - `embedding_model: str`, `embedding_dimensions: int`, `config_version: str`
  - `indexed_at: datetime`
- Built by the orchestrator from `EmbeddedChunk` + `DocumentEnvelope`

### Dimension consistency enforcement
- On construction, the orchestrator calls `ensure_schema(dimensions, metric)`
- Before upserting, assert every record's `embedding_dimensions` matches the schema's
  configured dimension count; mismatch raises `INDEXER_DIMENSION_MISMATCH` (PERMANENT)
- **Reject mixed-model batches**: if records in one call carry more than one distinct
  `embedding_model`, raise `INDEXER_MIXED_MODEL_BATCH` (PERMANENT). Mixed-model indexes
  silently destroy retrieval quality — fail loud.

### Two adapters
- **`AzureAISearchIndexer`** — production path. Wraps `azure-search-documents`.
  - `ensure_schema` creates the index with: `chunk_id` (key), `content` (searchable text),
    `content_vector` (Collection(Edm.Single), HNSW profile, cosine metric), and filterable
    fields for `doc_id`, `doc_version`, `allowed_groups`, `trust_tier`, `config_version`
  - HNSW params from config: `m`, `ef_construction`, `ef_search`
  - `max_batch_size=100`; checks per-item status on batch responses (AI Search fails per-document)
  - Credentials from env only (`AZURE_SEARCH_ENDPOINT`, `AZURE_SEARCH_API_KEY`)
- **`InMemoryIndexer`** — local, credentials-free path.
  - Dict keyed on `chunk_id`, plus a `doc_id → set[chunk_id]` secondary index for delete/count
  - `search(query_vector, top_k, filters) -> list[tuple[IndexRecord, float]]` — brute-force
    cosine similarity. **Included specifically so the end-to-end demo can prove retrieval works**,
    not just that writes succeed
  - Thread-safe (lock-guarded, matching `InMemoryLedgerStore`'s pattern)
  - `max_batch_size=1000`, `supports_hybrid=False`

### Configuration
- `indexer.yaml`:
  - `adapter: azure_ai_search | in_memory`
  - `index_name: vestibule-docs-v1`
  - `metric: cosine`
  - `hnsw.m: 4`, `hnsw.ef_construction: 400`, `hnsw.ef_search: 500`
  - `batch_size: null` (null = adapter's max)
  - `delete_before_upsert_on_version_change: true`
  - `retry.max_attempts: 5`, `retry.backoff_base_seconds: 2`, `retry.backoff_max_seconds: 60`
- Secrets from env only

### Failure classification (register on module import)
- `INDEXER_EMPTY_RECORDS` — PERMANENT (embedder returned zero chunks)
- `INDEXER_DIMENSION_MISMATCH` — PERMANENT (record dimensions ≠ schema dimensions)
- `INDEXER_MIXED_MODEL_BATCH` — PERMANENT (more than one embedding_model in a single call)
- `INDEXER_SCHEMA_CONFLICT` — PERMANENT (existing index has incompatible schema; requires
  human intervention, never retry)
- `INDEXER_RECORD_TOO_LARGE` — PERMANENT (a single record exceeds the store's size limit;
  typically an oversized table chunk from REQ-006 — this is where that advisory becomes real)
- `INDEXER_RATE_LIMITED` — TRANSIENT (429; respect `Retry-After`)
- `INDEXER_UPSTREAM_ERROR` — TRANSIENT (5xx)
- `INDEXER_TIMEOUT` — TRANSIENT
- `INDEXER_PARTIAL_BATCH_FAILURE` — TRANSIENT (some records in a batch failed; retry only
  the failed chunk_ids, not the whole batch)
- `INDEXER_INTERNAL` — TRANSIENT (unclassified; logs original)
- `INDEXER_DEPENDENCY_MISSING` — PERMANENT (azure-search-documents not installed but
  azure adapter requested)
- Add all codes to `config/errors.yaml` known_codes; add `ingestion.indexer.model` to
  `ingestion/errors/test_registry.py`'s hand-import list — same PR

### Retries
- `tenacity`: exponential backoff + jitter + max attempts, respecting `Retry-After`
- **Partial-batch retry**: on `INDEXER_PARTIAL_BATCH_FAILURE`, retry only the failed
  `chunk_id`s. Do not re-upsert the successful ones (wasteful, and idempotency makes it
  harmless but pointless)
- Every external call bounded by an explicit timeout

### Tests
- Unit: 250 records with `max_batch_size=100` produces exactly 3 upsert calls
- Unit: idempotency — indexing the same `EmbeddedChunk` list twice results in the same
  chunk count in the store (upsert, not duplicate)
- Unit: version change — indexing `doc_id=X, doc_version=v1` with 10 chunks, then
  `doc_id=X, doc_version=v2` with 6 chunks, leaves exactly 6 chunks for X (delete-before-upsert
  purged the orphans)
- Unit: dimension mismatch raises `INDEXER_DIMENSION_MISMATCH` (PERMANENT) before any write
- Unit: a batch containing two distinct `embedding_model` values raises
  `INDEXER_MIXED_MODEL_BATCH` (PERMANENT) before any write
- Unit: partial batch failure retries only the failed chunk_ids
- Unit: `allowed_groups` and `trust_tier` are present on every written record
- Unit: each failure code fires under its condition; PERMANENT terminalizes, TRANSIENT
  self-transitions with incremented attempts
- Unit: `ensure_schema` is idempotent — calling twice does not error or recreate
- Azure adapter tested with a recorded-response fake — no live API calls in CI
- In-memory adapter tested for real, including `search()` returning correctly ranked results
- Ledger integration: assert transitions on success and both failure classes
- Property-based: any list of well-formed `EmbeddedChunk`s produces a store state where
  `count_by_doc_id == len(chunks)`
- **End-to-end integration test**: a real fixture PDF through envelope → analyzer → chunker →
  embedder (FastEmbed) → indexer (in-memory), then a `search()` call that retrieves a chunk
  containing known text. **This is the Phase 2 acceptance test.**

## Out of scope

- Reranking
- Hybrid (keyword + vector) search — the schema supports it; wiring it is a future REQ

  retrieval-side concern)

## Acceptance criteria
1. Indexing 250 records with an adapter declaring `max_batch_size=100` makes exactly 3 upsert calls.
2. Indexing the same chunk list twice leaves the store with the same count as after the first run.
3. Re-indexing a document whose chunk count shrank (10 → 6) leaves exactly 6 chunks for that
   `doc_id` — no orphans.
4. A record whose `embedding_dimensions` differs from the schema raises
   `INDEXER_DIMENSION_MISMATCH` (PERMANENT) before any write occurs.
5. A call containing records from two different `embedding_model` values raises
   `INDEXER_MIXED_MODEL_BATCH` (PERMANENT) before any write occurs.
6. Every written `IndexRecord` carries `allowed_groups` and `trust_tier` from the envelope.
7. A partial batch failure results in a retry of only the failed `chunk_id`s.
8. `ensure_schema` called twice in a row succeeds without error and does not recreate the index.
9. **End-to-end: a fixture PDF ingested through the full pipeline with FastEmbed + InMemoryIndexer,
   followed by a `search()` for text known to be in the document, returns that document's chunk
   in the top 3 results — with zero cloud credentials configured.**
10. All eleven error codes appear in `ErrorRegistry.all_codes()`; `config/errors.yaml` and the
    sync test are updated in the same PR.

## Contract touchpoints
- **Arrival Envelope:** `allowed_groups`, `trust_tier`, `doc_version` are carried onto every
  record — this is where the governance metadata finally lands in a queryable store
- **Identity & Idempotency:** `chunk_id` is the store's primary key; upsert semantics mean
  retries overwrite. Delete-before-upsert on version change prevents orphans. This is the
  contract's payoff moment
- **State Ledger:** owns the `indexing` stage transitions, all via `is_benign_concurrent_loss`
- **Failure Taxonomy:** registers 11 codes; every exception mapped or wrapped in `INDEXER_INTERNAL`

## Budget
- p95 latency (in-memory, 100 records): < 100ms
- p95 latency (Azure AI Search, 100 records batched): < 3 seconds
- Cost per document: zero for in-memory; Azure AI Search billed per index size and query volume
- Memory: in-memory adapter holds all records by design (dev/test only, documented as such);
  Azure adapter streams batches with no full-corpus accumulation

## Market-awareness note
What this REQ deliberately gets right that hand-rolled indexers commonly get wrong:
- **Mixed-model rejection.** Vectors from two different embedding models in one index silently
  destroy retrieval — they live in incompatible coordinate spaces. Most pipelines have no guard.
- **Delete-before-upsert on version change.** Documents shrink. Without this, orphan chunks
  accumulate forever and return stale content. Almost nobody handles it.
- **Provenance in the index, not just the ledger.** `embedding_model`, `embedding_dimensions`,
  and `config_version` on every record is what makes a future model migration tractable.
- **Security-trimming metadata written at ingest.** ACLs must be filterable at query time,
  which means they must be on the record. Retrofitting means reindexing.
- **Per-item batch status.** Azure AI Search (and most stores) fail per-document within a batch.
  Treating a batch as all-or-nothing either loses records or re-writes successful ones.

The `IndexerAdapter` interface is designed so Qdrant, pgvector, Pinecone, Weaviate, and
Elasticsearch adapters plug in without orchestrator changes. Hybrid search is schema-supported
but not wired.
