# REQ-006 — Chunker

**Phase:** 2 · **Pipeline:** full · **GitHub issue:** #<open one now>

## Goal
Turn the Analyzer's structured elements (paragraphs, tables, headings, image captions) into
retrieval-ready chunks. This is the component that decides *what a chunk is* — the unit of
retrieval the whole downstream RAG experience runs on. Chunk too small and each vector is
context-starved noise; chunk too large and each vector is a fuzzy average of unrelated topics.
The Chunker resolves that tension by choosing a strategy per element type.

## In scope

### The Chunker interface
- `Chunker.chunk(envelope, elements) -> list[Chunk]` — orchestrator, chooses a strategy per element
- Owns the ledger transition: `chunking → embedding` on success, or `chunking → chunking` (self-transition, TRANSIENT) on retryable failure, `chunking → failed` on PERMANENT failure

### The Chunk model
- `Chunk` pydantic value class: `chunk_id, doc_id, position, element_types: list[ElementType], text: str, token_count: int, metadata: dict`
- `chunk_id = derive_chunk_id(doc_id, chunk_index)` — from REQ-002, deterministic
- `position` — ordinal in the document, so retrieval can reconstruct order if needed
- `metadata` includes the section path (heading breadcrumb, when known) and page numbers (when known)

### Three strategies, chosen automatically per element type
- **Recursive** — for `PARAGRAPH`, `LIST`, `CODE` elements. Split on paragraph/sentence/word boundaries, respect target token size, add configurable overlap.
- **Structure-aware** — for documents with `HEADING` elements. Each heading section becomes a chunk boundary; sections that exceed the target size fall back to recursive splitting within the section. Heading breadcrumb prepended to the chunk's metadata (`section_path: "1. Scope > 1.2 Definitions"`).
- **Table-atomic** — for `TABLE` elements. Each table is one chunk, regardless of size. Serialized as markdown for the chunk's `text` field. Table captions (if present) are prepended. No table is ever split mid-row.

### Chunk strategy selection
- Automatic: the Chunker examines the element stream and picks strategy per element.
- Element with `type=TABLE` → table-atomic.
- Any document containing `HEADING` elements → structure-aware for the prose regions between headings.
- Everything else → recursive.
- **No user-facing "strategy switch"** — the scenario config exposes only target chunk size, overlap, and (Phase 3+) per-vertical policy overrides.

### Configuration
- `chunker.yaml`:
  - `target_chunk_tokens: 512`
  - `overlap_tokens: 64`
  - `min_chunk_tokens: 40` — merge trailing chunks smaller than this into their predecessor
  - `max_chunk_tokens: 800` — hard ceiling for any single chunk (tables can violate this only if the table itself is larger; document the exception explicitly)
  - `token_counter: tiktoken_cl100k` — the tokenizer used; MUST match the embedding model's tokenizer downstream

### Failure classification (register on module import)
- `CHUNKER_EMPTY_ELEMENTS` — PERMANENT (analyzer returned zero elements; nothing to chunk)
- `CHUNKER_OVERSIZED_TABLE` — WARNING only (logs, does not fail; table exceeds max but is emitted as a single chunk anyway; downstream indexers may reject)
- `TOKENIZER_LOAD_FAILED` — TRANSIENT (tokenizer resource unavailable at chunk time; retry safe)
- `CHUNKER_INTERNAL` — TRANSIENT (any unclassified exception; logs the original)

### Tests
- Unit: recursive chunker on a prose-only document, asserts respect for target size, overlap, min-chunk merging
- Unit: structure-aware chunker on a document with headings, asserts each chunk carries its section breadcrumb and chunks respect heading boundaries
- Unit: table-atomic — a 20-row table produces exactly 1 chunk; a table larger than `max_chunk_tokens` produces 1 chunk plus a WARNING log
- Unit: mixed document (headings + paragraphs + a table + a list) produces a coherent chunk stream with correct strategy per region
- Unit: empty elements list raises `CHUNKER_EMPTY_ELEMENTS` (PERMANENT); ledger row ends in `failed`
- Unit: deterministic chunking — same elements input twice produces identical `chunk_id`s in identical order
- Ledger integration: assert transitions on both success and failure paths
- Property-based (hypothesis): any random sequence of well-formed elements produces a valid chunk stream (no oversize chunks except from atomic tables; no under-min chunks except last one)

## Out of scope
- Parent-child (small-to-big) retrieval — v0.3 or v0.4 headline
- Semantic chunking (embedding-based boundaries) — later, if evals justify it
- Contextual headers (LLM-generated one-line summary per chunk) — later
- Generated hypothetical questions — later
- Late chunking — later
- Actual embedding of chunks (REQ-007)
- Actual indexing of chunks (REQ-008)

## Acceptance criteria
1. Given the Analyzer's output for a digital PDF with headings, prose, and one table:
   - Structure-aware chunking is applied to prose regions
   - The table produces exactly one chunk
   - No prose chunk exceeds `max_chunk_tokens`
   - Every chunk has a valid `chunk_id` derived via REQ-002
2. Given a table containing 30 rows: exactly one `Chunk` is emitted for it, no matter its size.
3. Given elements from a plain-text document with no headings: recursive chunking is applied; overlap between consecutive chunks matches config; the last chunk is not smaller than `min_chunk_tokens` unless it's the only chunk.
4. Given identical `elements` input twice, `chunk()` produces byte-identical output (same chunks, same IDs, same order).
5. Given zero elements: `CHUNKER_EMPTY_ELEMENTS` fires (PERMANENT); ledger transitions to `failed`.
6. All new error codes appear in `ErrorRegistry.all_codes()` after module import.

## Contract touchpoints
- **Arrival Envelope:** consumed for `doc_id` only; no source-specific fields inspected.
- **Identity & Idempotency:** `chunk_id = derive_chunk_id(doc_id, chunk_index)` — deterministic; re-chunking the same elements produces identical IDs, so downstream upserts overwrite cleanly.
- **State Ledger:** owns the `chunking` stage transitions.
- **Failure Taxonomy:** registers 4 error codes; every exception is either mapped or wrapped in `CHUNKER_INTERNAL`.

## Budget
- p95 latency: < 500ms for a 20-page document (pure Python + tiktoken, no I/O).
- Cost per document: zero (no external calls; tokenization is local).
- Memory: streams elements; no accumulation of the whole document text in memory.

## Market-awareness note
The `Chunker` interface is designed so a future `SemanticChunker`, `ParentChildChunker`, or
`LLMBoundaryChunker` can be added as an alternative strategy in v0.3+ without changing
the Chunker orchestrator's public API. The `strategy: str` field in each `Chunk`'s metadata
records which strategy produced it, enabling downstream evaluation of strategy effectiveness.
