# REQ-005 — Document Analyzer

**Phase:** 2 · **Pipeline:** full · **GitHub issue:** #5

## Goal
Detect what kind of document is arriving and route it to the right parser, so downstream
chunking works on structured elements (paragraphs, tables, images, headings) rather than
on raw bytes or a single flattened text blob. This is the first component of Phase 2 —
the transition from "we know the document arrived" (Phase 1) to "we understand what's in it."

## In scope

### Type detection
- `detect_type(envelope, bytes_reader) -> DetectedType` — reads the first N bytes, checks
  magic bytes, returns a `DetectedType` value: `DIGITAL_PDF | SCANNED_PDF | DOCX | IMAGE | UNSUPPORTED`
- PDF sub-typing: probe the first 3 pages of a PDF for extractable text.
  If avg characters/page < threshold, classify as `SCANNED_PDF`; otherwise `DIGITAL_PDF`.
- Magic-byte checks, never extension-based.
- Explicit rejection of unsupported types with `ANALYZER_UNSUPPORTED_TYPE` (PERMANENT).

### Parser adapter interface
- `ParserAdapter` abstract base class with one method:
  `parse(envelope, bytes_reader) -> list[Element]`
- `Element` value class: `type: ElementType, text: str, metadata: dict, confidence: float | None`
- `ElementType` enum: `HEADING | PARAGRAPH | TABLE | LIST | IMAGE_CAPTION | CODE`
- Parsers are registered against `DetectedType` values in a `ParserRegistry`.

### Two parser adapters
- **`PyMuPDFParser`** — routes for `DIGITAL_PDF`. Local, cheap. Extracts text with page/paragraph
  boundaries. Wraps `pymupdf` (aka `fitz`).
- **`DocumentIntelligenceParser`** — routes for `SCANNED_PDF`. Managed OCR + layout via
  Azure Document Intelligence's `prebuilt-layout` model. Extracts text, tables (with row/column
  structure), and section headings.

### The analyzer itself
- `Analyzer.analyze(envelope, bytes_reader) -> list[Element]` — orchestrates:
  1. Transition ledger: `pending → analyzing`
  2. Call `detect_type`
  3. Look up parser in registry; if none registered, raise `ANALYZER_NO_PARSER` (PERMANENT)
  4. Call `parser.parse(envelope, bytes_reader)`, with per-call timeout
  5. Transition ledger: `analyzing → chunking` on success, or `analyzing → failed` on error
  6. Return the list of `Element`s

### Failure classification (register on module import)
- `ANALYZER_UNSUPPORTED_TYPE` — PERMANENT (unknown magic bytes, encrypted PDF, corrupt file)
- `ANALYZER_NO_PARSER` — PERMANENT (registry misconfiguration)
- `PARSER_TIMEOUT` — TRANSIENT (parser exceeded its per-call timeout)
- `DOCINT_RATE_LIMITED` — TRANSIENT (Azure DocIntel 429)
- `DOCINT_UPSTREAM_ERROR` — TRANSIENT (Azure DocIntel 5xx)
- `PARSER_INTERNAL` — TRANSIENT (any unclassified parser exception; logs the original)

### Configuration
- `analyzer.yaml`:
  - `scanned_pdf_probe_pages: 3`
  - `scanned_pdf_min_chars_per_page: 50`
  - `parser_timeout_seconds: 240`
  - `docint.endpoint`, `docint.api_version` (secrets via env only)

### Tests
- Unit: type detection for each supported type using fixture files, including corrupt/encrypted
  edge cases, empty files, extension-vs-content mismatches.
- Unit: registry lookup, missing-parser path, timeout path.
- Unit: PyMuPDF parser on a fixture digital PDF — asserts elements returned in reading order,
  no empty element list on a non-empty PDF.
- Unit: DocIntel parser is tested with a **recorded response fake** — no live API calls.
- Integration (opt-in via env flag `RUN_LIVE_DOCINT_TESTS=1`): one real DocIntel call on a
  scanned fixture. Skipped in CI unless the flag is set. Requires credentials.
- Ledger integration: assert transitions happen at the right points on both success and failure.

## Out of scope
- Chunking of elements (REQ-006).
- Table serialization strategy (belongs to the Chunker).
- Image captioning (VLM adapter — later phase).
- Cross-parser confidence scoring and auto-escalation (Phase 4 headline feature).
- Additional parser adapters beyond the two named (Docling, Unstructured, VLM parsers — later).
- Streaming of very large documents (v0.3 concern).

## Acceptance criteria
1. Given a digital PDF fixture, `Analyzer.analyze` returns ≥ 1 element per page with visible text,
   and the ledger row for that doc ends in status `chunking`.
2. Given a scanned PDF fixture and the recorded DocIntel response, `Analyzer.analyze` returns
   elements including at least one `TABLE` type when the fixture contains a table.
3. Given a file with a `.pdf` extension but non-PDF magic bytes, `Analyzer.analyze` raises
   `AnalyzerError` carrying `ANALYZER_UNSUPPORTED_TYPE`; ledger row ends in `failed`.
4. Given a supported type with no registered parser, `Analyzer.analyze` raises `AnalyzerError`
   carrying `ANALYZER_NO_PARSER`; classification is PERMANENT.
5. Given a parser that raises after the timeout, `PARSER_TIMEOUT` fires as TRANSIENT and the
   ledger records the failure without transitioning to a terminal state.
6. The two parser adapters can be swapped out for a `FakeParser` in tests without any changes
   to `Analyzer` or its callers — proven by the test suite doing exactly that.
7. All new error codes appear in `ErrorRegistry.all_codes()` after module import.

## Contract touchpoints
- **Arrival Envelope:** the Analyzer receives a valid envelope and never inspects source-specific
  metadata beyond it.
- **Identity & Idempotency:** re-analyzing the same `doc_id` produces the same set of elements
  given the same bytes (deterministic parsing where the underlying parser allows).
- **State Ledger:** owns the `analyzing` transitions; asserted by tests.
- **Failure Taxonomy:** registers 6 error codes; every parser exception is either mapped to a
  registered code or wrapped in `PARSER_INTERNAL`.

## Budget
- p95 latency (PyMuPDF on a 20-page digital PDF): < 3 seconds locally.
- p95 latency (DocIntel on a 10-page scanned PDF): < 60 seconds end-to-end (dominated by the
  upstream service).
- Cost per document: zero for PyMuPDF; ~$0.01–0.03 per page for DocIntel (billed upstream).
- Memory: streams pages when the parser supports it; no full-document in-memory materialization
  above 50 MB.

## Market-awareness note
This story ships PyMuPDF + Azure Document Intelligence for v0.2. The `ParserAdapter` and
`ParserRegistry` design deliberately allows future parsers (Docling, Unstructured, VLM-based
parsers, or newer entrants) to plug in as v0.3/v0.4 adapters without touching Analyzer code.
Add `benchmarks/` folder in this PR with a README explaining how future parser evaluations will
be run — the folder itself is the market-tracking commitment.
