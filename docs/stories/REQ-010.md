
# REQ-010 — Scenario Config Store

**Phase:** 3 · **Pipeline:** compressed (story → developer → reviewer, no LLD gate) · **GitHub issue:** #<open one>

## Goal
Store per-vertical ingestion settings as data, read at runtime, so different verticals can have
different configurations without redeployment and without affecting each other. This is what
turns Vestibule from a pipeline into a platform: an admin declares HR's settings and Legal's
settings independently, and the pipeline reads whichever applies to the document in front of it.

Two backends ship: YAML-file-backed (simple, version-controlled, good for tests and single-tenant
deployments) and Azure Table Storage (runtime-editable, for the platform case).

## In scope

### The Scenario model
- `Scenario` frozen pydantic model:
  - `scenario_id: str` — unique key, e.g. `"hr-policies-v2"`
  - `vertical: str` — e.g. `"hr"`, `"legal"`, `"finance"`
  - `config_version: str` — bumped on every edit; stamped onto chunks so config drift is traceable
  - `index_name: str`
  - `chunker: ChunkerSettings` — target_chunk_tokens, overlap_tokens, min/max_chunk_tokens
  - `embedder: EmbedderSettings` — adapter, model, target_dimensions
  - `indexer: IndexerSettings` — metric, hnsw params, dimensions
  - `acl_source: Literal["envelope", "blob_metadata", "source_system"]`
  - `default_trust_tier: str`
  - `enabled: bool` — soft-disable a scenario without deleting it
  - `created_at`, `updated_at`
- Nested settings models mirror the existing `ChunkerConfig`, `EmbedderConfig`, `IndexerConfig`
  shapes so a `Scenario` can produce the component configs the pipeline already expects
- `Scenario.to_chunker_config()`, `.to_embedder_config()`, `.to_indexer_config()` — converters

### The ScenarioStore interface
- Abstract base with:
  - `get(scenario_id: str) -> Scenario | None`
  - `get_by_vertical(vertical: str) -> Scenario | None` — returns the enabled scenario for that vertical
  - `list_all(include_disabled: bool = False) -> list[Scenario]`
  - `upsert(scenario: Scenario) -> Scenario` — bumps `config_version` and `updated_at`
  - `delete(scenario_id: str) -> bool`
- Properties: `is_writable: bool` — YAML backend is read-only; Table Storage backend is writable

### Two backends
- **`YamlScenarioStore`** — reads `config/scenarios/*.yaml` at construction, one file per scenario.
  Read-only: `upsert` and `delete` raise `SCENARIO_STORE_READ_ONLY` (PERMANENT).
  `is_writable = False`. Reloads on explicit `reload()` call, not automatically.
- **`TableStorageScenarioStore`** — Azure Table Storage backed, fully writable.
  Partition key = `vertical`, row key = `scenario_id`.
  `is_writable = True`. Credentials from env only.
  Optimistic concurrency via ETag on upsert; conflict raises `SCENARIO_CONFLICT` (TRANSIENT).

### Validation
- On construction, every scenario is validated:
  - `embedder.target_dimensions` must be ≤ the model's native dimensions (reject impossible truncation)
  - `indexer.dimensions` must equal `embedder.target_dimensions` (or native if no truncation) —
    **this is the dimension-consistency check that prevents the silent retrieval failure from
    mismatched embed/index dimensions**
  - `chunker.max_chunk_tokens` ≥ `target_chunk_tokens` ≥ `min_chunk_tokens`
  - `index_name` matches Azure AI Search naming rules (lowercase, alphanumeric + dashes, 2-128 chars)
- Validation failures raise `SCENARIO_INVALID` (PERMANENT) at load time, not at ingest time — fail fast

### Caching
- `CachedScenarioStore` decorator wrapping any backend, with configurable TTL (default 60s)
- Avoids a store read per document while keeping runtime edits reasonably fresh
- `invalidate(scenario_id)` for explicit cache busting after a known write

### Configuration
- `scenario_store.yaml`:
  - `backend: yaml | table_storage`
  - `yaml.directory: config/scenarios`
  - `table_storage.table_name: VestibuleScenarios`
  - `cache.enabled: true`, `cache.ttl_seconds: 60`
  - `default_scenario_id: null` — fallback when a document's vertical has no scenario
- Secrets from env only

### Failure classification (register on module import)
- `SCENARIO_NOT_FOUND` — PERMANENT (no scenario for the requested id or vertical, and no default configured)
- `SCENARIO_INVALID` — PERMANENT (validation failed; e.g. dimension mismatch, bad index name)
- `SCENARIO_STORE_READ_ONLY` — PERMANENT (write attempted against the YAML backend)
- `SCENARIO_CONFLICT` — TRANSIENT (optimistic-concurrency ETag conflict on upsert)
- `SCENARIO_STORE_UNAVAILABLE` — TRANSIENT (Table Storage 5xx or timeout)
- `SCENARIO_STORE_DEPENDENCY_MISSING` — PERMANENT (azure-data-tables not installed but table backend requested)
- Add all codes to `config/errors.yaml` known_codes; add `vestibule.scenario.model` to the
  test-registry hand-import list — same PR

### Tests
- Unit: `YamlScenarioStore` loads multiple scenario files; `get_by_vertical` returns the right one
- Unit: two scenarios with different chunk sizes are independently retrievable — **isolation is the
  core property; assert changing one does not affect the other**
- Unit: `upsert` on the YAML backend raises `SCENARIO_STORE_READ_ONLY` (PERMANENT)
- Unit: `upsert` on the table backend bumps `config_version` and `updated_at`
- Unit: a scenario whose `indexer.dimensions` ≠ `embedder.target_dimensions` raises
  `SCENARIO_INVALID` at load, before any ingestion
- Unit: `target_dimensions` exceeding the model's native dimensions raises `SCENARIO_INVALID`
- Unit: an invalid `index_name` raises `SCENARIO_INVALID`
- Unit: `to_chunker_config()`, `to_embedder_config()`, `to_indexer_config()` produce configs
  equivalent to what the pipeline components already accept
- Unit: `CachedScenarioStore` serves from cache within TTL, re-reads after expiry, and
  `invalidate` forces a re-read
- Unit: disabled scenarios are excluded from `get_by_vertical` and from `list_all` by default
- Table backend tested with a recorded-response fake — no live calls in CI
- Property-based: any valid `Scenario` round-trips through YAML serialization unchanged

## Out of scope
- The Vertical Loader that *uses* this store to route documents (REQ-009)
- Dynamic index creation from scenario settings (REQ-011)
- An admin UI or API for editing scenarios (Phase 5)
- Wiring the pipeline components to read from scenarios instead of their own yaml configs —
  that's REQ-009's integration work; this REQ ships the store and the converters
- Audit logging of scenario changes (later; note the gap in the story)
- Per-document scenario overrides

## Acceptance criteria
1. `YamlScenarioStore` pointed at a directory with `hr.yaml` and `legal.yaml` returns both via
   `list_all()`, and `get_by_vertical("hr")` returns the HR scenario.
2. HR and Legal scenarios with different `chunker.target_chunk_tokens` are independently
   retrievable; reading or modifying one has no effect on the other.
3. `upsert` against `YamlScenarioStore` raises `SCENARIO_STORE_READ_ONLY` (PERMANENT).
4. `upsert` against `TableStorageScenarioStore` increments `config_version` and updates `updated_at`.
5. A scenario with `embedder.target_dimensions=1024` and `indexer.dimensions=1536` raises
   `SCENARIO_INVALID` (PERMANENT) at store construction — not at ingest time.
6. `Scenario.to_embedder_config()` produces an `EmbedderConfig` the existing Embedder accepts
   without modification.
7. `CachedScenarioStore` with `ttl_seconds=1` serves the cached value on an immediate second
   read and re-reads after the TTL elapses.
8. A disabled scenario is not returned by `get_by_vertical` but is returned by
   `list_all(include_disabled=True)`.
9. All six error codes appear in `ErrorRegistry.all_codes()`; `config/errors.yaml` and the sync
   test are updated in the same PR.

## Contract touchpoints
- **Arrival Envelope:** the envelope's optional `scenario_id` and `vertical` fields are what a
  caller uses to look up a scenario; this REQ does not modify the envelope
- **Identity & Idempotency:** `config_version` from the resolved scenario is what gets stamped
  onto chunks, making config drift detectable — the Indexer already reads it from the ledger row
- **State Ledger:** no transitions owned by this component; it is a lookup, not a pipeline stage
- **Failure Taxonomy:** registers 6 codes

## Budget
- p95 latency: < 1ms per `get` when cached; < 20ms uncached YAML; < 50ms uncached Table Storage
- Cost per document: effectively zero with caching enabled (one store read per TTL window,
  not per document)
- Memory: YAML backend holds all scenarios in memory (bounded by scenario count, which is
  small by nature — one per vertical)
