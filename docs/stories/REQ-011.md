# REQ-011 — Dynamic Index Provisioning

**Phase:** 3 · **Pipeline:** full (story → LLD → design-review → developer → code-review) · **GitHub issue:** #<open one>

## Goal
Ensure a vertical's index exists before documents are written to it, creating it from a versioned
template when absent, safely under concurrency. Track what exists in a registry so the system can
answer "which indexes are live, from which template version, holding which embedding model."

This is the component that makes onboarding a new vertical a configuration change rather than an
infrastructure ticket: an admin defines a scenario, the first document arrives, and the index is
provisioned automatically with the right schema.

## In scope

### The IndexTemplate model
- `IndexTemplate` frozen pydantic model, loaded from `config/index_templates/*.yaml`:
  - `template_id: str` — e.g. `"standard-v1"`
  - `template_version: str` — bumped when the schema changes
  - `dimensions: int | None` — null means "inherit from the scenario's embedder settings"
  - `metric: Literal["cosine", "dotProduct", "euclidean"]`
  - `hnsw: HnswSettings` — m, ef_construction, ef_search
  - `fields: list[FieldSpec]` — the schema, expressed store-agnostically
  - `semantic_ranker_enabled: bool`
  - `hybrid_enabled: bool`
- `FieldSpec`: `name`, `type` (`key | text | vector | filterable_string | filterable_string_collection | filterable_datetime | retrievable_only`), `searchable: bool`
- A default `standard-v1` template ships in the repo, matching the schema REQ-008's
  `AzureAISearchIndexer.ensure_schema` currently creates — **this REQ generalizes that hardcoded
  schema into a template**

### The IndexRegistry
- Records every index this system has provisioned:
  - `index_name` (key), `vertical`, `scenario_id`, `template_id`, `template_version`
  - `dimensions`, `metric`, `embedding_model`
  - `created_at`, `last_verified_at`, `document_count: int | None`
  - `status: Literal["provisioning", "ready", "failed", "retired"]`
- Interface:
  - `get(index_name) -> IndexRegistryEntry | None`
  - `list_by_vertical(vertical) -> list[IndexRegistryEntry]`
  - `register(entry) -> IndexRegistryEntry` — idempotent; registering an existing name with
    identical settings is a no-op returning the existing entry
  - `mark_ready(index_name)`, `mark_failed(index_name, reason)`, `mark_retired(index_name)`
- Two backends, matching the ScenarioStore pattern from REQ-010:
  - `InMemoryIndexRegistry` — dev/test
  - `TableStorageIndexRegistry` — production, ETag-based optimistic concurrency

### The IndexProvisioner
- `IndexProvisioner.ensure(scenario) -> IndexRegistryEntry` — the single public entry point
- Flow:
  1. Look up `scenario.index_name` in the registry
  2. **Registry says ready** → verify the live index still matches (see drift detection), return
  3. **Registry has no entry** → attempt to claim provisioning (see concurrency below), create the
     index from the template, mark ready, return
  4. **Registry says provisioning** → another worker is mid-flight; wait with bounded backoff for
     it to reach ready, then return. Timeout → `INDEX_PROVISION_TIMEOUT` (TRANSIENT)
  5. **Registry says failed** → `INDEX_PROVISION_FAILED` (PERMANENT); requires human intervention
  6. **Registry says retired** → `INDEX_RETIRED` (PERMANENT)

### Concurrency — the load-bearing requirement
Two documents for a brand-new vertical can arrive simultaneously on different workers. Both will
find no registry entry and both will try to create the index.

- Claiming is done by an **atomic conditional insert** into the registry with status
  `provisioning`. Exactly one worker wins.
- The losing worker does not error — it detects the conflict and falls into the wait path (step 4).
- If the winning worker crashes mid-provision, the entry is stuck in `provisioning`. A
  `provisioning_stale_after_seconds` config (default 300) makes a stale claim reclaimable: a
  waiting worker past that threshold may re-claim via a second conditional write.
- **The underlying store's index creation must also be treated as racy** — a worker may win the
  registry claim and still find the index already exists in the store (created out of band).
  Treat "already exists with compatible schema" as success, not as an error.

### Drift detection
- On every `ensure()` where the registry says ready, verify the live index is still compatible:
  - Same dimensions
  - Same metric
  - Same or newer template_version
- Mismatch → `INDEX_SCHEMA_DRIFT` (PERMANENT). Never auto-migrate; schema changes to a live index
  holding vectors is a migration, not a provisioning concern.
- Verification is cached per `last_verified_at` with a configurable interval (default 300s) so this
  is not an API call per document

### Template resolution
- `scenario.index_template_id` selects the template; falls back to config's `default_template_id`
- `dimensions` resolution order: template's explicit value → scenario's embedder target_dimensions
  → adapter's native dimensions
- The resolved dimensions are validated against the scenario's embedder settings before creation;
  mismatch → `INDEX_TEMPLATE_INVALID` (PERMANENT) — **this is the same class of silent failure
  REQ-010's validation catches, enforced again at the provisioning boundary**

### The IndexProvisionerAdapter interface
- `index_exists(index_name) -> bool`
- `create_index(index_name, template, dimensions, metric) -> None`
- `describe_index(index_name) -> IndexDescription | None` — for drift detection
- `delete_index(index_name) -> None` — used only by `mark_retired` flows, never automatically
- Two implementations:
  - `AzureAISearchProvisioner` — translates `IndexTemplate` into an Azure AI Search index definition
  - `InMemoryProvisioner` — for tests and the local path; backed by the same dict the
    `InMemoryIndexer` uses, so the local end-to-end flow provisions and then writes

### Configuration
- `index_provisioning.yaml`:
  - `registry_backend: in_memory | table_storage`
  - `default_template_id: standard-v1`
  - `template_directory: config/index_templates`
  - `provisioning_stale_after_seconds: 300`
  - `verification_interval_seconds: 300`
  - `wait_for_provisioning_timeout_seconds: 60`
  - `auto_create: true` — when false, a missing index raises rather than provisioning
- Secrets from env only

### Failure classification (register on module import)
- `INDEX_TEMPLATE_NOT_FOUND` — PERMANENT
- `INDEX_TEMPLATE_INVALID` — PERMANENT (dimensions mismatch, invalid field spec, bad index name)
- `INDEX_SCHEMA_DRIFT` — PERMANENT (live index incompatible with template)
- `INDEX_PROVISION_FAILED` — PERMANENT (registry marked failed; needs human intervention)
- `INDEX_RETIRED` — PERMANENT
- `INDEX_AUTO_CREATE_DISABLED` — PERMANENT (index missing and `auto_create: false`)
- `INDEX_PROVISION_TIMEOUT` — TRANSIENT (waited too long for another worker's provision)
- `INDEX_PROVISION_CONFLICT` — TRANSIENT (registry ETag conflict; retry resolves)
- `INDEX_REGISTRY_UNAVAILABLE` — TRANSIENT (registry backend 5xx/timeout)
- `INDEX_PROVISIONER_UNAVAILABLE` — TRANSIENT (search service 5xx/timeout during creation)
- `INDEX_PROVISIONER_DEPENDENCY_MISSING` — PERMANENT
- Add all codes to `config/errors.yaml`; add `vestibule.provisioning.model` to the test-registry
  hand-import list — same PR

### Tests
- Unit: `ensure()` on an unknown index creates it, registers it, marks ready, returns the entry
- Unit: `ensure()` on a ready index returns immediately without calling `create_index`
- Unit: **concurrency — two `ensure()` calls racing for the same new index result in exactly one
  `create_index` call**; the loser waits and returns the same entry. This is the core test.
- Unit: a stale `provisioning` entry (older than `provisioning_stale_after_seconds`) is reclaimable;
  a fresh one is not
- Unit: `create_index` failing after a successful registry claim marks the entry `failed`, and a
  subsequent `ensure()` raises `INDEX_PROVISION_FAILED` (PERMANENT) rather than retrying forever
- Unit: the store reporting "index already exists with compatible schema" after a won claim is
  treated as success
- Unit: a live index with different dimensions than the template raises `INDEX_SCHEMA_DRIFT`
- Unit: drift verification is skipped within `verification_interval_seconds` and performed after
- Unit: `auto_create: false` with a missing index raises `INDEX_AUTO_CREATE_DISABLED`
- Unit: template dimensions inconsistent with the scenario's embedder settings raises
  `INDEX_TEMPLATE_INVALID` before any index is created
- Unit: `register` is idempotent — registering identical settings twice returns the same entry
- Unit: registry ETag conflict raises `INDEX_PROVISION_CONFLICT` (TRANSIENT)
- Unit: `standard-v1` template produces an index definition equivalent to what REQ-008's
  hardcoded `ensure_schema` created — **regression guard against the generalization changing behavior**
- Azure provisioner tested with a recorded-response fake; no live calls in CI
- Property-based: any valid template plus any valid scenario produces a well-formed index definition
- **End-to-end**: the quickstart flow extended so a brand-new vertical provisions an in-memory
  index and then successfully indexes and retrieves — proving provision-then-write works locally

## Out of scope
- Shadow indexes and alias swaps for reprocessing (Phase 4)
- Automatic schema migration of live indexes (deliberately excluded — this is a data migration,
  not provisioning; `INDEX_SCHEMA_DRIFT` fails loudly instead)
- Index deletion or retirement automation (`mark_retired` and `delete_index` exist, but nothing
  calls them automatically)
- Service-limit budgeting (max indexes per Azure tier) — worth a follow-up issue
- Per-tenant index isolation beyond per-vertical
- Cost tracking per index

## Acceptance criteria
1. `ensure(scenario)` for a vertical with no existing index creates it from the resolved template,
   registers it as ready, and returns an entry whose `dimensions` matches the scenario's embedder
   `target_dimensions`.
2. A second `ensure(scenario)` for the same scenario returns the existing entry without calling
   `create_index`.
3. **Two concurrent `ensure()` calls for the same new index result in exactly one `create_index`
   invocation, and both callers receive an equivalent ready entry.**
4. A registry entry stuck in `provisioning` for longer than `provisioning_stale_after_seconds`
   is reclaimable by a waiting worker; one fresher than that threshold is not, and the waiter
   times out with `INDEX_PROVISION_TIMEOUT` (TRANSIENT).
5. If `create_index` raises after the registry claim is won, the entry is marked `failed` and a
   subsequent `ensure()` raises `INDEX_PROVISION_FAILED` (PERMANENT).
6. A live index whose dimensions differ from the resolved template raises `INDEX_SCHEMA_DRIFT`
   (PERMANENT); no automatic migration is attempted.
7. With `auto_create: false`, a missing index raises `INDEX_AUTO_CREATE_DISABLED` (PERMANENT).
8. A template whose resolved dimensions conflict with the scenario's embedder settings raises
   `INDEX_TEMPLATE_INVALID` before any index is created.
9. The `standard-v1` template produces an index definition equivalent to REQ-008's previously
   hardcoded schema.
10. End-to-end locally: a new vertical is provisioned, a document is indexed into it, and a search
    retrieves the document — zero cloud credentials.
11. All eleven error codes appear in `ErrorRegistry.all_codes()`; `config/errors.yaml` and the sync
    test are updated in the same PR.

## Contract touchpoints
- **Arrival Envelope:** not read directly; the scenario resolved by REQ-009 is the input
- **Identity & Idempotency:** `ensure()` is idempotent — calling it repeatedly for the same
  scenario produces the same result and at most one index creation. This is the contract's
  hardest test yet, because idempotency must hold *across processes*, not just across retries
  in one process
- **State Ledger:** owns no document-level transitions; this operates on index lifecycle, not
  document lifecycle. The registry is a separate store from the ledger by design — indexes
  outlive documents
- **Failure Taxonomy:** registers 11 codes. Note the deliberate split: everything requiring human
  intervention (drift, failed provision, retired) is PERMANENT; everything resolvable by waiting
  or retrying is TRANSIENT

## Budget
- p95 latency: < 5ms when the registry says ready and verification is cached; < 2s for a first
  provision against Azure AI Search; < 60s worst case when waiting on another worker
- Cost per document: effectively zero after the first (one cached registry read)
- Memory: templates and registry entries held in memory, bounded by index count

## Market-awareness note
Index lifecycle management is the clearest gap in this space. Every RAG framework — LangChain,
LlamaIndex, Haystack, Unstructured — assumes the index already exists and was created by someone
else, out of band. Managed platforms create one index for you and stop there.

What this component does that has no equivalent:
- **Versioned templates in source control.** The schema is a reviewable artifact, not a
  provisioning script someone ran once and lost.
- **Create-on-first-document, safely under concurrency.** The atomic-claim pattern is the
  difference between "works in a demo" and "works with eight workers behind a queue."
- **Drift detection that refuses to auto-migrate.** Silently altering a live index holding
  vectors is how corpora get corrupted. Failing loudly is the correct behavior and almost nobody
  implements it.
- **A registry answering "what exists, from which template, holding which model."** The
  prerequisite for the Phase 4 reprocessing lane — you cannot swap an embedding model safely
  without knowing what your current indexes are.
