# REQ-009 — Vertical Loader

**Phase:** 3 · **Pipeline:** compressed (story → developer → reviewer, no LLD gate) · **GitHub issue:** #<open one>

## Goal
Decide which vertical an arriving document belongs to, then load that vertical's scenario so the
pipeline runs with the right settings and writes to the right index. Documents whose vertical
cannot be confidently determined are parked for human review rather than guessed at — a
misrouted document gets the wrong ACLs, which is a security failure, not a routing inconvenience.

## In scope

### The VerticalResolution model
- `VerticalResolution` frozen pydantic model:
  - `vertical: str | None`
  - `scenario_id: str | None`
  - `source: ResolutionSource` — how it was determined
  - `confidence: Literal["explicit", "inferred", "unresolved"]`
  - `reason: str` — human-readable explanation, surfaced in the review queue
- `ResolutionSource` enum: `ENVELOPE_SCENARIO_ID | ENVELOPE_VERTICAL | SOURCE_MAPPING | UNRESOLVED`

### The VerticalLoader
- `VerticalLoader.resolve(envelope) -> VerticalResolution` — decides, does not load
- `VerticalLoader.load(envelope) -> tuple[Scenario, VerticalResolution]` — resolves then fetches
  the scenario from the `ScenarioStore`; parks the document if unresolved

### Resolution order (first match wins, most explicit first)
1. **`envelope.scenario_id` is set** → look it up directly. Confidence `explicit`.
   If the scenario doesn't exist, that is an error (`SCENARIO_NOT_FOUND`), not a park —
   someone named a scenario that isn't there.
2. **`envelope.vertical` is set** → `store.get_by_vertical(vertical)`. Confidence `explicit`.
   No enabled scenario for that vertical → `SCENARIO_NOT_FOUND` (PERMANENT). Again an error,
   not a park: the vertical was stated, the config is missing.
3. **Source mapping matches** → a configured rule maps `envelope.source` (e.g.
   `"blob:hr-uploads"`) to a vertical. Confidence `inferred`.
4. **Nothing matched** → park for review. Confidence `unresolved`.

### Source mapping
- Configured in `vertical_loader.yaml` as an ordered list of rules:
```yaml
  source_mappings:
    - match: "blob:hr-*"        # glob against envelope.source
      vertical: "hr"
    - match: "sharepoint:legal-site"
      vertical: "legal"
```
- Exact matches take precedence over globs; among globs, the first listed rule wins
- Rules are validated at construction: every mapped vertical must have an enabled scenario in
  the store, else `VERTICAL_MAPPING_INVALID` (PERMANENT) at startup — fail fast, not at ingest

### The review queue (minimal)
- New ledger status: `NEEDS_REVIEW`
- Legal transitions added to REQ-003's table:
  - `pending → needs_review` (parked by the loader)
  - `needs_review → pending` (a human resolved it; re-enters the pipeline)
  - `needs_review → failed` (a human rejected it)
  - `needs_review` is **not** terminal — that's the point
- `ReviewQueue` class with three operations:
  - `list_pending(limit=100) -> list[ReviewItem]` — ledger rows in `needs_review`, newest first
  - `assign(doc_id, scenario_id) -> None` — sets the scenario, transitions back to `pending`
  - `reject(doc_id, reason) -> None` — transitions to `failed` with `VERTICAL_REJECTED`
- `ReviewItem`: `doc_id`, `source`, `blob_path`, `reason`, `parked_at`, `suggested_verticals: list[str]`
- `suggested_verticals` is a convenience only: verticals whose source mappings *nearly* matched
  (same prefix before the first delimiter). Not a classifier — no guessing, just a hint for the human.

### Parking, precisely
- When resolution is `unresolved`, the loader:
  1. Writes `reason` onto the ledger row (`last_error_message`)
  2. Transitions `pending → needs_review` via `is_benign_concurrent_loss` triage
  3. Raises `VERTICAL_UNRESOLVED` (PERMANENT) so the caller stops processing this document
- **PERMANENT is correct here even though the document isn't dead:** retrying will produce the
  identical result, because nothing about the document changes on redelivery. Only a human
  action (`assign`) changes the outcome. Document this reasoning in the code — it is the
  non-obvious part of this component.

### Configuration
- `vertical_loader.yaml`:
  - `source_mappings: []` — the ordered rule list above
  - `park_unresolved: true` — when false, unresolved raises `VERTICAL_UNRESOLVED` without
    parking (for deployments that don't want a review queue)
  - `review_queue.suggest_verticals: true`
- No secrets

### Failure classification (register on module import)
- `VERTICAL_UNRESOLVED` — PERMANENT (no rule matched; document parked)
- `VERTICAL_MAPPING_INVALID` — PERMANENT (a source mapping references a vertical with no
  enabled scenario; raised at construction)
- `VERTICAL_REJECTED` — PERMANENT (a human rejected the parked document)
- `REVIEW_ITEM_NOT_FOUND` — PERMANENT (assign/reject called for a doc_id not in `needs_review`)
- Reuses `SCENARIO_NOT_FOUND` (PERMANENT) from REQ-010 for stated-but-missing scenarios
- Add all codes to `config/errors.yaml`; add `vestibule.vertical.model` to the test-registry
  hand-import list — same PR

### Tests
- Unit: envelope with `scenario_id` set resolves to that scenario, source `ENVELOPE_SCENARIO_ID`,
  confidence `explicit`
- Unit: envelope with only `vertical` set resolves via `get_by_vertical`, confidence `explicit`
- Unit: envelope with neither, but matching a source mapping glob, resolves with confidence `inferred`
- Unit: exact source mapping wins over a glob that also matches
- Unit: among two matching globs, the first listed rule wins
- Unit: envelope matching nothing parks the document — ledger row ends in `needs_review`, and
  `VERTICAL_UNRESOLVED` (PERMANENT) is raised
- Unit: `park_unresolved: false` raises without transitioning the ledger to `needs_review`
- Unit: stated `vertical` with no enabled scenario raises `SCENARIO_NOT_FOUND`, does **not** park —
  **this distinction is the core of the design and must be tested explicitly**
- Unit: a source mapping referencing an unknown vertical raises `VERTICAL_MAPPING_INVALID` at
  loader construction, before any document is processed
- Unit: `ReviewQueue.list_pending` returns parked items newest first, respects limit
- Unit: `assign(doc_id, scenario_id)` transitions `needs_review → pending` and sets the scenario
- Unit: `reject(doc_id, reason)` transitions `needs_review → failed` with `VERTICAL_REJECTED`
- Unit: `assign` for a doc_id not in `needs_review` raises `REVIEW_ITEM_NOT_FOUND`
- Unit: a parked document that is assigned and re-processed resolves successfully the second
  time — **the round trip is what proves the review queue is real and not a dead end**
- Unit: REQ-003's transition table rejects illegal transitions into and out of `needs_review`
  (e.g. `indexed → needs_review` must raise)
- Property-based: any envelope produces exactly one `VerticalResolution` with a non-empty `reason`

## Out of scope
- A UI for the review queue (Phase 5)
- Classifier-based vertical inference (LLM or heuristic content classification) — deliberately
  excluded; guessing at ACL-relevant routing is the failure mode this component exists to prevent
- Bulk assign/reject operations
- Notification or alerting when the review queue grows (worth a follow-up issue)
- Wiring the loader into the pipeline orchestration — this REQ ships the component; integration
  is the caller's job until a pipeline orchestrator exists
- Dynamic index creation for a newly resolved vertical (REQ-011)

## Acceptance criteria
1. An envelope with `scenario_id="hr-policies-v2"` loads that scenario, `source=ENVELOPE_SCENARIO_ID`,
   `confidence="explicit"`.
2. An envelope with `vertical="legal"` and no `scenario_id` loads the enabled legal scenario,
   `confidence="explicit"`.
3. An envelope with neither, whose `source="blob:hr-uploads"` matches the mapping `"blob:hr-*"`,
   loads the HR scenario with `confidence="inferred"`.
4. An envelope matching no rule transitions its ledger row to `needs_review` and raises
   `VERTICAL_UNRESOLVED` (PERMANENT). The ledger row is **not** `failed`.
5. An envelope with `vertical="marketing"` where no marketing scenario exists raises
   `SCENARIO_NOT_FOUND` and does **not** park — a stated-but-missing vertical is a config error,
   not an ambiguity.
6. A source mapping referencing a vertical with no enabled scenario raises
   `VERTICAL_MAPPING_INVALID` at loader construction.
7. `ReviewQueue.assign(doc_id, "hr-policies-v2")` on a parked document returns it to `pending`;
   re-running `load()` then resolves successfully.
8. REQ-003's ledger rejects `indexed → needs_review` as an illegal transition.
9. All four new error codes appear in `ErrorRegistry.all_codes()`; `config/errors.yaml` and the
   sync test are updated in the same PR.

## Contract touchpoints
- **Arrival Envelope:** reads `scenario_id`, `vertical`, and `source`. Does not modify the envelope.
- **Identity & Idempotency:** resolution is a pure function of the envelope plus configuration —
  the same envelope with the same config always resolves identically. Parking is idempotent:
  parking an already-parked document is a benign no-op, not an error.
- **State Ledger:** introduces the `needs_review` status and its transitions. **This extends
  REQ-003's transition table**, which is a deliberate, additive contract change — document it in
  the CHANGELOG under Changed, and update REQ-003's legal transition table in
  `docs/designs/REQ-003-lld.md`'s live reference (not the frozen historical record — add a note
  pointing at this REQ instead).
- **Failure Taxonomy:** registers 4 codes; reuses `SCENARIO_NOT_FOUND` from REQ-010.

## Budget
- p95 latency: < 5ms per resolution (glob matching plus one cached scenario lookup)
- Cost per document: zero
- Memory: source mappings held in memory, bounded by rule count

## Market-awareness note
Most RAG frameworks assume a single index and single configuration — routing is left entirely to
the caller. What this component does that is uncommon:
- **Refuses to guess on ACL-relevant routing.** Classifier-based vertical inference is the
  obvious feature and is deliberately excluded: a misclassified document lands in an index with
  the wrong `allowed_groups`, meaning the wrong people can retrieve it. Parking for review is
  slower and correct; classification is faster and occasionally a data breach.
- **Distinguishes ambiguity from misconfiguration.** A document with no vertical is ambiguous
  (park it). A document declaring a vertical that has no scenario is a config error (fail it).
  Collapsing these two into one behavior is the common mistake.
- **`needs_review` as a non-terminal ledger state.** Most pipelines have only success and
  failure; documents needing human input get marked failed and forgotten. A parked state that
  can return to the pipeline is what makes human-in-the-loop actually work.
