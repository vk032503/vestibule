# REQ-012 — Poison Queue Reprocessor

**Phase:** 3 · **Pipeline:** compressed (story → developer → reviewer, no LLD gate) · **GitHub issue:** #<open one>

## Goal
Give operators a way to act on documents the pipeline could not process: see what failed and why,
requeue documents whose root cause has been fixed, and archive documents that will never succeed.
This closes the operational loop Phase 3 opened — every component can send a document to `failed`;
until now, nothing could bring one back.

Requeue semantics for v0.3: **reset to `pending` and reprocess from the top.** Contract #2 makes
this safe — deterministic IDs mean re-done work overwrites cleanly rather than duplicating.
Resume-from-stage is a future optimization requiring intermediate-state persistence, deliberately
out of scope.

## In scope

### The FailedItem model
- `FailedItem` frozen pydantic model, built from a ledger row plus registry context:
  - `doc_id`, `source`, `blob_path` (from the ReviewRegistry pattern where available, else None)
  - `stage: str` — where it failed (analyzing, chunking, embedding, indexing)
  - `error_code: str`, `error_message: str | None`
  - `severity: Severity` — looked up from the ErrorRegistry
  - `attempts: int`, `failed_at: datetime`, `first_ingested_at: datetime`
  - `assigned_scenario_id: str | None`

### The Reprocessor
- `Reprocessor.list_failed(limit=100, error_code=None, stage=None, since=None) -> list[FailedItem]`
  — ledger rows in `failed`, newest first, filterable by error code, stage, and time window
- `Reprocessor.summarize() -> FailureSummary` — counts grouped by error_code and by stage;
  the "what's actually going wrong" view. `FailureSummary` includes total, per-code counts,
  per-stage counts, and oldest/newest failure timestamps
- `Reprocessor.requeue(doc_id) -> RequeueResult` — transitions `failed → pending` so the document
  re-enters the pipeline from the top
- `Reprocessor.requeue_by_error_code(error_code, limit=100) -> BatchRequeueResult` — bulk requeue
  for the common case: "the DocIntel outage is over; requeue everything that failed with
  DOCINT_UPSTREAM_ERROR." Processes up to `limit`, returns per-doc success/failure
- `Reprocessor.archive(doc_id, reason) -> None` — transitions `failed → archived`; terminal,
  for documents that will never succeed and should stop appearing in `list_failed`

### Ledger changes (additive, same pattern as REQ-009's needs_review)
- New status: `ARCHIVED` — terminal
- New legal transitions:
  - `failed → pending` (requeue; the previously-terminal `failed` becomes exitable **only via
    this explicit operator action** — pipeline code still cannot transition out of failed)
  - `failed → archived` (archive)
  - `archived` → nothing (terminal)
- `requeue` resets `attempts` to 0 and clears `last_error_code`/`last_error_message` — the
  document gets a fresh run; its history is preserved in `first_ingested_at` and log output
- All transitions via `is_benign_concurrent_loss` triage, matching every other ledger write

### Requeue safety
- `requeue` on a doc_id not in `failed` raises `REPROCESS_NOT_FAILED` (PERMANENT) — you can only
  requeue failures; documents in flight or indexed are untouchable
- Requeue is idempotent in effect: requeuing, having the document fail again, and requeuing again
  is safe and bounded by operator action, not an automatic retry loop
- `requeue_by_error_code` skips (does not error on) documents that left `failed` between listing
  and requeuing — concurrent operator actions are benign
- **No automatic requeuing anywhere.** This component is human-triggered by design; automatic
  retry belongs to the TRANSIENT taxonomy and queue redelivery, which already exist. This tool
  is for failures those mechanisms correctly gave up on

### Configuration
- `reprocessor.yaml`:
  - `default_list_limit: 100`
  - `max_batch_requeue: 500` — hard cap on bulk requeue per call
- No secrets

### Failure classification (register on module import)
- `REPROCESS_NOT_FAILED` — PERMANENT (requeue/archive called on a doc not in `failed`)
- `REPROCESS_DOC_NOT_FOUND` — PERMANENT (unknown doc_id)
- Add both to `config/errors.yaml`; add `vestibule.reprocessor.model` to the test-registry
  hand-import list — same PR

### Tests
- Unit: `list_failed` returns only `failed` rows, newest first, respects limit and filters
  (error_code, stage, since)
- Unit: `summarize` groups correctly by code and stage on a mixed set of failures
- Unit: `requeue` transitions `failed → pending`, resets attempts to 0, clears error fields
- Unit: `requeue` on a `pending`/`indexed`/`needs_review` doc raises `REPROCESS_NOT_FAILED`
- Unit: `requeue` on an unknown doc_id raises `REPROCESS_DOC_NOT_FOUND`
- Unit: `archive` transitions `failed → archived`; archived docs no longer appear in `list_failed`
- Unit: `archived` is terminal — no transition out (ledger table enforcement test)
- Unit: pipeline code still cannot transition out of `failed` — only the Reprocessor's explicit
  operations can (the transition is legal in the table, but assert the semantic boundary is
  documented and the previous terminality tests are updated deliberately, not silently)
- Unit: `requeue_by_error_code` requeues only matching docs, respects `max_batch_requeue`,
  returns accurate per-doc results, and skips docs that concurrently left `failed`
- Unit: **round trip** — a document that failed at embedding is requeued, reprocessed through
  the full local pipeline, and ends `indexed`. Deterministic IDs mean the re-run overwrites:
  assert the final index holds exactly one copy of each chunk (Contract #2's payoff proven
  end-to-end)
- Property-based: any sequence of requeue/archive operations on a set of failed docs leaves the
  ledger in a consistent state with no doc in an illegal status

## Out of scope
- Resume-from-stage requeue (requires intermediate-state persistence; future optimization)
- Automatic requeue policies (scheduled retries, auto-requeue on dependency recovery) —
  deliberately excluded; this is a human tool
- A UI (Phase 5); this REQ ships the programmatic interface an admin API/UI will call
- Notification/alerting when failures accumulate (worth a follow-up issue)
- Requeuing `needs_review` documents — that's the ReviewQueue's job (REQ-009), already shipped
- Dead-letter integration with actual Azure Storage queues (the queue adapter is Phase 5 infra)

## Acceptance criteria
1. `list_failed()` on a ledger containing failed, indexed, and needs_review docs returns only the
   failed ones, newest first.
2. `list_failed(error_code="DOCINT_UPSTREAM_ERROR")` returns only matching failures.
3. `summarize()` on 10 failures across 3 error codes and 2 stages returns correct counts per code
   and per stage.
4. `requeue(doc_id)` on a failed doc transitions it to `pending` with attempts=0 and cleared
   error fields.
5. `requeue` on a doc in any status other than `failed` raises `REPROCESS_NOT_FAILED` (PERMANENT).
6. `archive(doc_id, reason)` transitions to `archived`; the doc no longer appears in
   `list_failed()`; no transition out of `archived` is legal.
7. `requeue_by_error_code` requeues at most `max_batch_requeue` docs and reports per-doc outcomes.
8. **Round trip: a doc failed at embedding, requeued, reprocessed through the full local pipeline
   (FastEmbed + InMemoryIndexer), ends `indexed`, and the index contains exactly one copy of each
   chunk.**
9. Both error codes appear in `ErrorRegistry.all_codes()`; `config/errors.yaml` and the sync test
   updated in the same PR.

## Contract touchpoints
- **Arrival Envelope:** not read directly; operates on ledger state
- **Identity & Idempotency:** the requeue round trip is Contract #2's proof in production form —
  reprocessing overwrites rather than duplicates, which is the entire reason reset-to-pending is
  safe. AC8 tests this end-to-end
- **State Ledger:** extends the transition table with `archived` and the operator-only
  `failed → pending` exit. This is the second additive transition-table change (after REQ-009's
  needs_review); CHANGELOG under Changed, and a pointer note in REQ-003's LLD same as before
- **Failure Taxonomy:** registers 2 codes; consumes the registry to enrich FailedItem with severity

## Budget
- p95 latency: < 10ms for list/summarize on in-memory ledger; requeue is one ledger write
- Cost per operation: zero (no external calls)
- Memory: list operations bounded by limit; summarize streams counts

## Market-awareness note
Dead-letter queues exist in every messaging system, but they operate on *messages*, not on
domain state: a DLQ tells you a message failed, not which document, at which stage, with which
classified error, after how many attempts. Because Vestibule's ledger already holds all of that,
this component is small — the hard work was done by Contracts #2–4. That's the point worth
making: failure operations are nearly free when the plumbing was built right, and nearly
impossible when it wasn't. No RAG framework ships this because none of them have the ledger
underneath it.
